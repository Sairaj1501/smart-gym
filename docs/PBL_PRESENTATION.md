# PBL presentation pack

## Title
AI-Powered Smart Gym Management System

## Abstract
Small gyms still run on registers and spreadsheets: renewals are missed, dues are mis-added and nobody notices a regular member quietly stop coming. This project is a web platform that manages memberships, attendance, payments and trainers, lets members track their own fitness privately, generates trainer-reviewed diet and workout plans, and alerts staff when a member's attendance drops, using only real check-in records.

## Problem statement
Gym owners lose revenue and members through missed renewals, inaccurate dues and late follow-up; members get generic plans and no visibility of their progress.

## Existing system and limitations
Paper registers or spreadsheets: no automatic expiry, duplicate or wrong payments, no attendance analysis, no access control, no member-facing view, no progress tracking.

## Proposed system
One integrated, role-based, database-driven web application with automatic expiry maths, history-preserving renewals, duplicate-proof payments, per-member privacy, rule-based planners with trainer review, and engagement alerts.

## Objectives
1. Remove manual expiry and balance calculation. 2. Prevent duplicate attendance and payments. 3. Give each role only the data it needs. 4. Help trainers act on data (drop-off alerts, plan review). 5. Keep health data private and consent-based. 6. Run on free tiers with no paid service required.

## Novelty (honest version)
Not a new model, but a combination rarely seen in student gym projects: engagement alerts from real attendance; plans that are generated by rules and then *approved by a human trainer*; consent-gated health tracking with deletion; payment logic that is safe under concurrency without database transactions; every AI feature has a working non-AI fallback.

## Functional requirements
Registration and profiles; plan assignment, renewal, change; attendance with QR; payments and receipts; trainer assignment and PT scheduling without overlap; health metrics and charts; diet and workout generation and review; notifications; reports with CSV; analytics dashboard.

## Non-functional requirements
Security (JWT, bcrypt, server-side authorization, validation, rate limiting, audit log), privacy (consent, deletion, role isolation), usability (responsive, empty/loading/error states), maintainability (layered, AI replaceable), cost (free tier friendly).

## Technology justification
React for role-based dashboards; Express for a thin REST layer; MongoDB for flexible plan documents plus strict indexes where integrity matters; Recharts for charts from live aggregates; zod for validation; Node's built-in test runner to avoid extra dependencies.

## Architecture / ER / DFD / use cases

## Testing strategy
Pure logic (dates, BMI, engagement, diet and workout engines, chatbot rules, CSV) is unit-tested with Node's runner. Workflows (login, role access, duplicate member, payment overpayment and concurrency, renewal history, duplicate check-in, consent, allergen safety, review gating, notifications, reports) are covered by API integration tests against an in-memory MongoDB. Report only the results in `TEST_EXECUTION_LOG.md` that you have personally run.

## Expected outcomes
Fewer missed renewals, accurate dues, faster check-in, earlier follow-up of fading members, plans reviewed by a person.

## Limitations
See README "Known limitations". Say them first; judges respect that.

## Future scope
Payment gateway with server-side verification, email/SMS reminders, progress photos with consent, mobile app/PWA, multi-branch, a real nutrient database (IFCT/USDA), a trained churn model once enough history exists.

## 7-minute demo script
1. Admin dashboard: KPIs and charts come from the database (point at the demo-data banner). 2. Staff registers a member with a plan and partial payment; show the one-time password and the outstanding balance. 3. Double-click Record payment: only one receipt. Try overpaying: refused. 4. Renew: history keeps the old record, new term starts the day after the old one ends. 5. Check in twice: second attempt is rejected. Try an expired member: blocked. 6. Log in as member1: dashboard, QR code, health tracking consent. 7. Generate a diet plan with "peanuts, dairy" as allergies; show none appear and the disclaimer. Generate a workout; show it waits for trainer approval. 8. Trainer logs in, approves it. 9. Admin Attendance page: `member1` (inactive) and `member2` (declining) are flagged with the reason. 10. Reports: CSV download. Close with limitations and future scope.

## Likely judge questions
*Where is the AI?* Be exact: planners and alerts are rules and statistics; the LLM is optional and only explains or chats. *What if the API key fails?* Fallback answers automatically. *Is health data safe?* Consent, role isolation, audit log, deletion. *Can staff see health data?* No.
